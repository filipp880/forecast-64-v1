# Идея: суммировать дневной прогноз по календарным неделям

Старая модель прогнозирует 64 отдельных дня. Можно для каждой пары склад–артикул сложить прогнозы с понедельника по воскресенье и получить недельные суммы. Это отдельный кандидат для сравнения с моделью, которая сразу учится на недельных целях; дневной SMAPE около 29% не переносится на недельные суммы автоматически.

## Где лежат модель и доказательства

Все пути относительно `E:\Dev_Cpp\forecast-64-v1`:

- `artifacts/recovery/legacy64-20261027/forecast-container/model/model.pkl` — финальные веса дневного ансамбля.
- В той же папке `config.json` и `preprocessor.pkl` — настройки и препроцессор. Ансамбль: 0,3 hurdle + 0,7 LightGBM, горизонт 64 дня.
- `artifacts/recovery/original-20261022/forecast-container/app/` — исходный дневной код, включая расчёт признаков и метрик.
- `artifacts/repository-before-root-layout-20261028/experiments/legacy_source/original-20261022/forecast-container/` — дополнительный снимок исходного проекта.
- `artifacts/recovery/legacy64-20261027/FINAL_REPORT_RU.md` — отчёт о проверке дневного решения.
- `artifacts/repository-before-root-layout-20261028/experiments/evidence/daily/verified/verified_summary.json` — оценки исторических вариантов.
- `artifacts/repository-before-root-layout-20261028/experiments/evidence/daily/verified/2026-03-25/` и `2026-05-28/` — материалы оценочных окон; перед использованием проверить наличие весов и сохранённых прогнозов.

Проверенные дневные оценки исходного рецепта: SMAPE 28,9149%, WAPE 77,2646% на 26.03–28.05; SMAPE 29,5890%, WAPE 73,7051% на 29.05–31.07. Они относятся к дневным целям и другим окнам, чем текущие недельные исследования.

## Как проверять

1. Для исторической отсечки взять только доступную на тот момент историю. Нужен оценочный checkpoint, не обученный на проверяемых продажах. Финальные старые веса обучены до 31.07.2026: их нельзя использовать как честный тест на прошлом и для текущего прогноза с отсечкой 26.07.
2. Получить дневные прогнозы, записать `week = date - weekday(date)` и просуммировать quantity по `week, warehouse_name, article`.
3. Фактические продажи агрегировать тем же способом. Брать только полные календарные недели и одинаковый каталог пар для всех сравниваемых вариантов. Отсутствующие дни продаж считать нулями только внутри известного наблюдаемого периода; отсутствующий день прогноза не подменять молча нулём.
4. Посчитать все пять недельных метрик и сравнить с прямым недельным прогнозом на тех же датах. Проверить сумму дневных и недельных прогнозов, покрытие, дубли и границы.
5. При полезном самостоятельном результате проверить небольшое смешивание дневного агрегированного и прямого недельного прогнозов.

Для девяти недель нужно 63 дня. Только если начало совпадает с понедельником, 64-дневного горизонта достаточно на девять полных недель с исключением последнего дня. При другом старте внутри 64 дней может не поместиться девять полных календарных недель: нужно изменить отсечку или расширить дневной горизонт и переобучить. Для текущего итогового периода нужны 27.07–27.09, а не произвольные группы по семь дней.

При необходимости нового обучения подготовить один запуск для PyCharm и передать пользователю; обучение в чате не запускать. Сначала сравнить уже сохранённые честные прогнозы, если они доступны. Преимущество идеи пока не доказано.
