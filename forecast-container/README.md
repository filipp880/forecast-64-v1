# Forecast Container — прогноз продаж по складам и товарам

Сервис из задания со звёздочкой (`Nonton_Backend_TZ_Forecasting_API`): HTTP-API на FastAPI
для прогноза `quantity` на 64 календарных дня вперёд по парам «склад × артикул».

> Статус: `Dockerfile`, `.dockerignore` и `docker-compose.yml` в репозитории. Перед
> сборкой образа обучите модель (`train.py`), иначе контейнер поднимется, но
> `POST /predict` будет отвечать `503 MODEL_NOT_READY`.

## 1. Описание решения

- **Модель:** зарегистрированы четыре типа моделей (адаптеры в `app/models/` за
  общим интерфейсом `BaseForecastModel`, выбор — флагом `--model-type` при обучении
  и полем `model_type` в `config.json`):
  - `blend` — **финальная модель**: взвешенная смесь hurdle и lgbm
    (вес `weight_hurdle=0.3`); на бэктесте по 8 срезам доминирует обе одиночные
    (SMAPE 28.3% при 28.4–28.6% у одиночных);
  - `lgbm` — одиночный бустинг (`LGBMRegressor`, таргет `log1p(quantity)`);
  - `hurdle` — классификатор P(продажа > 0) + Poisson-регрессор величины
    (архитектура под нулевую природу данных);
  - `catboost` — альтернативный бустинг.
  Постобработка прогноза (порог обнуления, округление до целых) общая для всех
  моделей — см. «Обучение модели».
- **Признаки** (модуль `app/features.py`, общий для обучения и инференса):
  - календарь целевого дня: `h` (горизонт 1..64), день недели, месяц, день, неделя года, выходной;
  - статистика серии по состоянию на дату отсечки: средние за 7/14/28/56/90 дней,
    доля нулей за 28/90 дней, последнее значение, дней с последней продажи,
    тренд `mean_28/mean_90`, число продажных дней за 90 дней, профиль по дню недели;
  - остатки: последний остаток, средний за 28 дней, доля нулей за 90 дней,
    запас покрытия `stock / mean_28`;
  - категориальные: `warehouse_name`, `article`, `category_lvl_1..3`, `characteristic`;
  - продажи агрегируются по департаментам/городам (ТЗ: суммируются в паре «склад × товар»).
- **Ключевое требование сценария с контейнером:** все признаки считаются по истории
  не глубже **180 дней** до даты отсечки — ровно столько данных приходит через API,
  поэтому одна и та же модель работает и на обучении, и в сервисе.
- **Инференс:** срез последних 180 дней → признаки на 64 дня вперёд → обратный
  трансформ таргета → клиппинг в `[0, ∞)` → постобработка из `config.json`
  (порог обнуления, округление) → кэш. GET-эндпоинты отдают нарезки из кэша.
- **Детерминизм:** фиксированные `random_seed` и `thread_count`, обучение на CPU;
  повторный запуск на тех же данных даёт тот же прогноз.

Обучающий скрипт: `train.py` (подробности — «Обучение модели»). Пока модель не обучена,
`/health` и валидация работают, а `POST /predict` возвращает `503 MODEL_NOT_READY`.

## 2. Сборка (Docker)

База — `python:3.11-slim`. Сборка из директории `forecast-container/`:

```bash
docker build -t forecast-api .
```

Файл обученной модели (`model/model.pkl` у blend/hurdle, `model/model.txt` у lgbm;
имя берётся из `config.json`) попадает в образ на момент сборки, поэтому обучите
модель заранее (`python train.py ...` — см. «Запуск»); без неё контейнер стартует,
но `POST /predict` вернёт `503 MODEL_NOT_READY`.

Требования: Docker ≥ 24, GPU не обязателен (обучение и инференс на CPU).
Ограничения ТЗ: сборка ≤ 60 мин, образ ≤ 30 GB, RAM ≤ 64 GB.

## 3. Запуск

Локально (Python 3.10+):

```bash
cd forecast-container
pip install -r requirements.txt
python train.py --sales ../data/sales_dataset_hakaton_train.csv \
                --stock ../data/stock_dataset_hakaton_train.csv \
                --out-dir model
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Запуск контейнера:

```bash
docker run -p 8000:8000 forecast-api
# или одной командой через compose:
docker compose up --build
```

Перед тестами API нужны сэмплы с историей ≥180 дней:

```bash
python scripts/make_samples.py
bash tests/test_api.sh
```

## 4. API

| Эндпоинт | Вход | Выход |
|---|---|---|
| `GET /health` | — | `{"status": "ok", "model_loaded": true}` |
| `POST /predict` | multipart: `sales`, `stock` (CSV, ≥180 дней истории) | `text/csv`, прогноз на 64 дня (562 496 строк на полных данных) |
| `GET /predict?article=&warehouse=` | хотя бы один из параметров | `text/csv`, срез кэша (нужен предварительный POST) |
| `GET /predict/all?format=csv\|json` | `format` (по умолчанию `csv`) | весь прогноз целиком |

Валидация POST: обязательные колонки, даты `YYYY-MM-DD`, история ≥180 дней (иначе `422`),
отрицательный `quantity` (иначе `422`), пустой файл/ошибка парсинга (`400`).
Отрицательный `stock` **допускается** (решение судей: в данных организаторов такие
строки есть) — панель клиппит его в 0, как при обучении.
Формат ошибок: `{"detail": "...", "code": "VALIDATION_ERROR"}`.

Браузерные клиенты: CORS открыт — по умолчанию все origins, список разрешённых
задаётся переменной окружения `CORS_ORIGINS` (через запятую, например
`http://localhost:5173`).

```bash
# Полный прогноз по загруженным данным
curl -X POST http://localhost:8000/predict \
  -F "sales=@data/sample_sales_6mo.csv" \
  -F "stock=@data/sample_stock_6mo.csv" \
  -o forecast.csv

# Прогноз по артикулу / складу / паре
curl "http://localhost:8000/predict?article=char_article_0" -o article_forecast.csv
curl "http://localhost:8000/predict?warehouse=warehouse_name_0" -o warehouse_forecast.csv
curl "http://localhost:8000/predict?article=char_article_0&warehouse=warehouse_name_0" -o pair_forecast.csv

# Весь прогноз
curl "http://localhost:8000/predict/all?format=csv" -o full_forecast.csv
curl "http://localhost:8000/predict/all?format=json" -o full_forecast.json
```

### Обучение модели

```bash
cd forecast-container
python train.py --model-type lgbm                    # lgbm, значения по умолчанию: ../data/... и model/
python train.py --max-cutoffs 4 --model-params '{"n_estimators": 300}'  # быстрая проба
python train.py --model-type hurdle                # hurdle: P(продажа>0) x Poisson-величина
python train.py --model-type blend                 # финальная: 0.3 x hurdle + 0.7 x lgbm
python train.py --model-type lgbm --model-params '{"objective": "tweedie", "tweedie_variance_power": 1.5, "target_transform": "none"}'  # счётчики напрямую (эксперимент)
```

Класс `lgbm` принимает в `--model-params` не только гиперпараметры, но и
`objective` (`poisson`/`tweedie`), `tweedie_variance_power`, `alpha` и
`target_transform` (`log1p` по умолчанию). Вариант «objective на сырых
счётчиках» обучен и проверен (`logs/report_tweedie.json`) — на бэктесте он
уступает log1p-модели и в ансамбль не добавляется, см. «Лаборатория
постобработки».

Схема — строгий holdout по времени (защита от утечки):

1. **Обучающие срезы** — только те, чьи таргеты заканчиваются до окна отбора:
   сетка срезов каждые `--cutoff-step` дней (по умолчанию 28), признаки строго
   «на дату среза» (история ≤ 180 дней).
2. **Early stopping** — на окне отбора: предпоследние 64 дня данных.
3. **Пять метрик ТЗ** — на тестовом окне: последние 64 дня, которых ранняя
   остановка не видела; метрики сохраняются в `model/config.json`
   (`validation.metrics`, `validation.early_stopping`).
4. **Финальный refit** — модель «в бой» переобучается на всех срезах (включая
   последние дни) с зафиксированным числом итераций из шага 2; отключается
   флагом `--no-refit`.

Модель выбирается флагом `--model-type` (параметры — `--model-params` JSON поверх
значений по умолчанию). В `model/` записываются три файла: сама модель
(`model.txt`), `preprocessor.pkl` (спецификация пайплайна предобработки —
`predictor` сверяет её при загрузке) и `config.json`. При малом объёме данных
скрипт сам откатывается к простой схеме (train = все срезы кроме последнего).

Во время обучения в терминале виден прогресс: этапы с общим прошедшим временем
(`--- Обучение с early stopping: train 3 1.. строк ---`), по срезам — `[i/n]`
и оценка остатка, по итерациям LightGBM — `итерация 600/3000 (прошло, осталось ~)`
плюс метрика каждые `log_period` итераций (по умолчанию 200; чаще —
`--model-params '{"log_period": 100}'`). У CatBoost частоту задаёт `verbose`.

**Постобработка прогноза — главный рычаг после признаков.** Флаги
`--zero-threshold` (обнулять прогнозы ниже порога) и `--round-int` (округлять
до целых) применяются к метрикам валидации и записываются в `config.json` →
`postprocess`; инференс API применяет ровно те же шаги. Под определением SMAPE
п. 5.5 (дни «факт=0, прогноз=0» входят как 0%) маленькие плюсы на «спящих»
сериях приносят максимум штрафа, а нули — награду, поэтому порог стоит
подбирать сразу после каждой тренировки — без переобучения:

```bash
python train.py --max-cutoffs 4 --zero-threshold 0.5 --round-int --no-refit --tag "порог 0.5"
python evaluate.py --sweep-thresholds 0,0.25,0.5,1    # таблица метрик по порогам (с округлением и без)
```

**Журнал экспериментов.** Каждый прогон дописывает строку в `experiments.csv`
(метка `--tag "что меняли"`, параметры, число итераций, все пять метрик,
длительность) — сравнение вариантов по нему:

```bash
python train.py --max-cutoffs 4 --model-params '{"n_estimators": 500}' --no-refit \
    --tag "база (быстрый протокол)" --out-dir model_exp
```

Рекомендуемая лестница проверки изменений: **быстрый протокол** (~5–15 мин:
`--max-cutoffs 4 --no-refit`, сравнение по дельте метрик с базой)
→ **средний** (все срезы, `--no-refit`, ~30–60 мин — для сомнительных случаев)
→ **полный прогон** для финальной модели. Отключить журнал — `--no-log`.

### Как заменить или добавить модель

Весь код обучения/инференса работает через интерфейс `BaseForecastModel`
(`app/models/base.py`), поэтому замена модели — это один флаг `--model-type`,
а добавление новой — один новый класс:

1. Создайте класс-наследник `BaseForecastModel` в `app/models/` (примеры:
   `lightgbm_model.py` — одиночный бустер, `hurdle_model.py` — композиция
   «классификатор + регрессор», `blend_model.py` — ансамбль двух моделей реестра)
   и реализуйте `fit` / `predict` /
   `save` / `load`; объявите `name`, `file_suffix` и `default_params()`.
   Если у модели есть свои требования к признакам (кодирование категориальных
   и т.п.) — инкапсулируйте их внутри класса: контракт `fit`/`predict` не меняется,
   `train.py` и `predictor.py` о деталях не знают. Если имена гиперпараметров
   не совпадают с колонками журнала (`iterations`, `depth`, `learning_rate`),
   объявите маппинг `JOURNAL_PARAM_KEYS` — журнал `experiments.csv` заполнится
   корректно.
2. Зарегистрируйте класс в `MODEL_REGISTRY` (`app/models/__init__.py`).
3. При необходимости добавьте библиотеку в `requirements.txt` и пересоберите образ.
4. Обучите: `python train.py --model-type <имя>`. Инференс подхватит новую модель
   автоматически — тип читается из `config.json`.

Категориальные признаки: LightGBM и catboost принимают строки нативно (LightGBM —
через pandas `category` с фиксацией кодировки внутри класса модели). Если новая модель
строк не принимает (например, sklearn), её кодирование (`OrdinalEncoder` и т.п.) и
обучение энкодера инкапсулируются в классе модели — интерфейс `fit`/`predict` и
остальной код не меняются. Трансформ таргета — атрибут класса `target_transform`
(по умолчанию `log1p`).

### Проверка качества модели

ТЗ оценивает прогноз по пяти метрикам: **SMAPE (50%), WAPE (20%), RMSE (15%),
|Bias| (10%), RMSLE (5%)**. Реализация — в `app/metrics.py` по формулам ТЗ
(п. 5.2 и 5.5: дни «факт=0, прогноз=0» входят в SMAPE как 0% — решение судей;
шаблон `score.py` из раздела 9 исключал такие дни). Серии с нулевым средним
исключаются из Bias.

- `train.py` в конце печатает все пять метрик на тестовом окне (последние 64 дня,
  которых не видела ранняя остановка) и сохраняет их в `model/config.json` →
  `validation` (схема, срезы отбора/теста, горизонт, строки, метрики, число
  итераций) — «карточка модели» для сравнения запусков.
- `evaluate.py` — честный бэктест: берёт несколько последних **полных** срезов,
  считает для каждого прогноз по данным «до среза» и выводит метрики по каждому
  срезу, среднее и разбивку по горизонтам 1–7 / 8–28 / 29–64 дней:

```bash
python evaluate.py                                             # 8 последних полных срезов, шаг 28 дней
python evaluate.py --max-cutoffs 4 --cutoff-step 56            # быстрее
python evaluate.py --out report.json                           # сохранить JSON-отчёт
python evaluate.py --sweep-thresholds 0,0.25,0.5,1             # подбор порога обнуления без переобучения
```

Постобработка (порог обнуления, округление до целых) берётся из `config.json` →
`postprocess` и переопределяется флагами `--zero-threshold` / `--round-int` —
бэктест считает ровно то, что контейнер отдаст на инференсе.

Нюанс: по умолчанию финальная модель дообучается на всех срезах (`--refit`), поэтому
исторические срезы `evaluate.py` были и в её обучении — метрики оптимистичны
(честная вневыборочная оценка — `validation` из `train.py`). Для бэктеста
«как на соревновании» обучите с `--no-refit` — модель будет знать только срезы
до окна отбора — и прогоните `evaluate.py` по последним полным срезам.

### Лаборатория постобработки

Проверка идей «непрерывный прогноз → целые» и состава ансамбля без переобучения:
дамп сырых компонент финального бленда (`p`, `m`, `lgbm`) на 8 срезах бэктеста
и оценка ~35 вариантов постобработки + блока весов (3-компонентный бленд с
Tweedie, Duan-smearing, горизонтные и сегментные веса) по пяти метрикам ТЗ
с композитным индексом (1.0 = текущая прод-постобработка) и LOO-проверкой:

```bash
python scripts/dump_backtest_raw.py --model-dir model_blend   # логи и p/m/lgbm по срезам, ~100 c
python scripts/dump_backtest_raw.py --model-dir model_blend --extra-model model_tweedie  # + колонка extra_raw
python scripts/postproc_lab.py                                # отчёт logs/postproc_lab.json
python scripts/postproc_lab.py --out logs/postproc_lab_catboost.json  # вариант с другой третьей компонентой (--extra-model model_catboost)
python scripts/feature_lab.py                                 # база 28 признаков vs +5 recency, logs/feature_lab.json (~10 мин)
```

### Диагностика потолка: бюджет деревьев и разложение SMAPE

Последний формально неисследованный рычаг — бюджет деревьев — закрыт
(`scripts/budget_lab.py`: base-модель при 1500 vs 5000 итераций, те же срезы):

```bash
python scripts/budget_lab.py    # отчёт logs/budget_lab.json (~20 мин)
```

Выводы (2026-07): **больший бюджет не помогает, а вредит** (индекс 1.0042,
SMAPE 29.99 → 30.12, WAPE 79.3 → 79.8). ES по валидации не срабатывает даже
на 5000 деревьях — RMSE в log-пространстве на окне отбора продолжает
улучшаться, но метрики ТЗ на честных тестовых срезах деградируют: модель
дообучает специфику окна отбора, и валидационный RMSE перестаёт быть
референсом для композита (лимит 1500, в который упирались все лаборатории,
проблемой не был).

Почему лосс непреодолим — арифметика метрики на этих данных (разложение
среднего SMAPE по типам ячеек, дамп бэктеста, срезы 2026-01-10/05-02):

- 0/0 — 80-81% дней, вклад 0;
- **+/0 («продажа была, прогноз 0») — 10% дней, вклад 19.6-20.4 п.п.
  (69-74% всего лосса)**, штраф ровно 200% за день;
- 0/+ («ложная единица») — 2.3-2.8% дней, 17-20% лосса;
- +/+ — 6-7.5% дней, 10-11% лосса (средний штраф 43%).

Цена дня +/0 фиксирована метрикой, а break-even для «поставить единицу» —
p=0.5: на пропущенных днях вероятность модели не превышает 0.43 даже в 90-м
перцентиле (медиана 0.21) при идеальной калибровке p (средний p = реальная
доля продаж в каждом дециле). Поэтому любое «додать единиц» (флоры, веса ×5,
P_any/TSB, гейты, множители, sum+topK) в среднем обязано ухудшать SMAPE —
что все лаборатории и подтвердили. Модель сидит в байесовски оптимальном
консервативном углу под ТЗ-метрику, а Bias 91.7 — сознательная плата за
минимум SMAPE (вес 10% против 50%). Наблюдаемый уровень 27.7-29.4 — потолок
генератора данных: день покупки — бернуллиевский шум, невидимый признакам.

## 6. Известные ограничения

- Модель уже лежит в репозитории (`model/model.pkl`, ~4.4 МБ) и попадает в образ
  при сборке — сервис работает сразу после сборки, обучение `train.py` не обязательно
  (скрипт нужен для переобучения; он перезаписывает артефакты в `model/`). Если файла
  модели нет, `POST /predict` отвечает `503 MODEL_NOT_READY`, GET-эндпоинты — `400`.
- В данных организаторов нет `cost_price` и `volume_weight` (см. `data/нюансы.txt`) —
  валидатор их не требует; они принимаются, если присутствуют.
- Колонка остатков приходит как `article` в текущей выгрузке (в ТЗ — `char_article`);
  валидатор и панель принимают оба имени.
- Отрицательный `stock` в выгрузке встречается (≈57 строк во всём train): по решению
  судей POST его **не отклоняет** (часть п. 10.4 о 422 игнорируется), панель клиппит
  такие значения в 0 — модель учится и работает в одном пространстве.
- В train-выборке фактически 8777 пар «склад × товар» (11 × 799 полной сетки, но 12 пар
  не встречаются), поэтому прогноз строится по парам из переданных данных.
- `GET /predict/all` на полных данных (8777 пар × 64 дня, измерено 2026-10):
  `format=json` ≈ 55 МБ (строится в памяти), `format=csv` ≈ 27 МБ (отдаётся
  потоково) — оба за секунды; POST полного train-набора (~550 МБ суммарно)
  обрабатывается ≈ 35 с. GET-эндпоинты без предшествующего POST возвращают `400`.
- Оценка в `train.py` — одно 64-дневное окно отбора и одно тестовое (честные, но
  одиночные). Более устойчивая картина — `evaluate.py` (бэктест по нескольким
  полным срезам с разбивкой по горизонтам), с поправкой на перекрытие с обучением
  (см. «Проверка качества модели»).
