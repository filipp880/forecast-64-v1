# Forecast Container — прогноз quantity на 64 дня

## 1. Описание решения

Финальный комплект: `model/model.pkl`, `model/preprocessor.pkl`, `model/config.json`. Тип модели — `blend`: 0,3 × hurdle + 0,7 × LightGBM на `log1p(quantity)`, обратное преобразование и округление до целого неотрицательного значения. Hurdle тоже реализован на LightGBM: классификатор оценивает вероятность продажи, Poisson-регрессор — величину при положительном спросе. При вероятности ниже 0,5 hurdle возвращает ноль; это гейтирование, а не произведение вероятности на величину.

Глобальная модель использует 28 признаков: склад, товар и категории; средние продажи за 7/14/28/56/90 дней; частоту нулей, давность и тренд продаж; профиль дня недели; календарь целевой даты, горизонт и исторические остатки. Прогноз direct: признаки строятся из прошлого, будущие фактические продажи и остатки не требуются. История ограничена 180 днями, горизонт — 64 дня.

`stock_policy=window` использует только доступные к origin наблюдения остатков внутри истории. Для нескольких остатков одного дневного ключа используется max: оснований менять неизвестную бизнес-семантику на сумму нет. Совместимость исправленной предобработки с сохранённым Booster проверена на полном входе и двух OOF-окнах.

## 2. Сборка

Из корня репозитория:

```bash
cd forecast-container
docker build -t forecast-api .
```

Нужен работающий Docker с поддержкой Linux-контейнеров и Compose v2 для команды `docker compose`. База — Python 3.11 slim, CPU; GPU/CUDA не требуются. Зависимости зафиксированы в `requirements.lock.txt`, подключённом из `requirements.txt`. `libgomp1` устанавливается явно. Для сборки нужны сеть и доступ к реестру образов/PyPI; для инференса интернет не требуется.

Контекст сборки ограничен приложением, финальной моделью и зависимостями. Обучающие CSV, тестовые результаты, лаборатории и рабочие документы в образ не попадают.

## 3. Запуск

```bash
docker run --rm -p 127.0.0.1:8000:8000 forecast-api
# Альтернатива из этой же папки:
docker compose up --build
```

Проверка: `http://localhost:8000/health`. Swagger: `http://localhost:8000/docs`.

`MODEL_DIR` задаёт каталог модели, по умолчанию `model` относительно рабочей папки; внутри Docker — `/app/model`. `CORS_ORIGINS` — разрешённые origin через запятую, по умолчанию `*`. Для MVP можно задать `http://localhost:5173`.

22.10.2026 образ успешно собран; полный HTTP-инференс проверен внутри изолированной сети Docker без интернета. Два POST: 47,4 и 46,6 секунды; результаты побайтно одинаковы между собой и по значениям совпадают с подготовленным submission. Пик памяти сервиса — 5,84 ГиБ при лимите 7 ГиБ RAM и 8 CPU. GET полного CSV — 0,79 с, JSON — 0,47 с. Это измерения конкретного запуска Docker Desktop, не гарантированные времена на любом оборудовании. Браузерное соединение Windows с опубликованным портом в этот изолированный тест не входило.

Лимиты ТЗ: сборка до 60 минут, образ до 30 GB, RAM до 64 GB, POST до 60 минут, GET до 10 минут. На инференсе все входные данные приходят через API; скрытого чтения обучающей выборки нет.

## 4. API

| Эндпоинт | Вход | Результат |
|---|---|---|
| GET /health | — | status и model_loaded |
| POST /predict | multipart-файлы sales и stock | CSV прогноза на следующие 64 дня |
| GET /predict | article и/или warehouse | Срез последнего успешного POST |
| GET /predict/all | format=csv или json | Полный кэшированный прогноз |

```bash
curl -f -X POST http://localhost:8000/predict -F "sales=@data/sample_sales_6mo.csv" -F "stock=@data/sample_stock_6mo.csv" -o forecast.csv
curl -f "http://localhost:8000/predict?article=char_article_0" -o article.csv
curl -f "http://localhost:8000/predict?warehouse=warehouse_name_0" -o warehouse.csv
curl -f "http://localhost:8000/predict?article=char_article_0&warehouse=warehouse_name_0" -o pair_forecast.csv
curl -f "http://localhost:8000/predict/all?format=json" -o forecast.json
```

Выходные колонки строго `date,warehouse_name,article,quantity`. Начало горизонта — следующий день после max(sales.date). GET требует успешного POST; неизвестный идентификатор возвращает CSV только с заголовком.

Приоритет имеют уточнения судей из локального `../data/Нюансы 111.txt`: cost_price/volume_weight не обязательны; отрицательные stock принимаются и при построении признаков клиппируются в ноль; верные нули включаются в среднее SMAPE.

Stock принимает `article` или `char_article`; конфликт одновременно заданных имён отклоняется. Даты — YYYY-MM-DD. Нечисловые/NaN/inf в quantity/stock и пустые склад/артикул отклоняются. Отрицательный quantity запрещён. Пропуски неиспользуемых финансовых полей и категорий допустимы.

Минимальная глубина — интервал 180 календарных дней включительно. Редкий спрос не обязан иметь запись в каждый день. Две записи на границах полугодия не означают полноценную информативную историю — проверяется календарная глубина доступных данных. Будущие stock игнорируются.

Пустой/нечитаемый файл → 400; нарушение схемы/значений или отсутствие multipart → 422; незагруженная модель → 503; GET без фильтра/кэша → 400. Ошибки имеют `detail` и `code`; коды: VALIDATION_ERROR, MODEL_NOT_READY, FORECAST_NOT_READY.

## 5. Тесты и воспроизведение

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests -q
# После запуска API; нужны Bash, curl и Python:
bash tests/test_api.sh http://localhost:8000
```

27 регрессионных тестов проверяют валидацию, временные границы, метрики, загрузку артефактов и API. HTTP-самопроверка использует `data/sample_*_6mo.csv`; файлы `sample_sales.csv` и `sample_stock.csv` — первые 100 строк для примера формата, глубины истории для успешного POST в них недостаточно. Оба вида примеров включены в Git согласно уточнению судей. Выходы тестов — локальная `.test-output/`.

Полные данные организаторов нужно отдельно поместить в корневой `../data/`. Их нет ни в Git, ни в образе.

```bash
# Подготовка примеров, если данные/срез изменились:
python scripts/make_samples.py
# Генерация сдаваемого CSV:
python generate_submission.py --sales ../data/sales_dataset_hakaton_train.csv --stock ../data/stock_dataset_hakaton_train.csv --out ../submission/forecast.csv
```

Генератор проверяет 64 последовательные даты, покрытие наблюдаемых пар, отсутствие повторов/NaN/inf/отрицательных значений и детерминизм. Создаёт manifest с SHA-256. Существующий CSV не перезаписывается без `--overwrite`.

Для независимой проверки рецепта модели и сравнения с округлёнными mean28/mean90/dow:

```bash
python scripts/verified_backtest.py --out ../artifacts/verified
python scripts/select_candidate.py --out ../artifacts/verified
python scripts/select_candidate.py --out ../artifacts/verified --confirm
```

Первое origin 25.03.2026 — выбор, второе 28.05.2026 — подтверждение. Каждая оценочная копия обучается только на доступном ей прошлом; подбор числа деревьев использует предшествующий временной блок. Сетка кандидатов фиксируется до чтения результатов. Контрольное окно не используется для повторного выбора другого кандидата. Локальное сравнение по пяти метрикам не является официальным rank-score.

Итог сохранён в `logs/verified_summary.json`; подробные OOF, протокол и оценочные модели генерируются локально в `../artifacts/verified/`. На подтверждении исходного рецепта: SMAPE 29,5890%, WAPE 73,7051%, RMSE 0,9144, абсолютный относительный Bias 91,6975%, RMSLE 0,3325. Это независимая историческая оценка, а не score будущего submission. Подтверждённого улучшения рецепта не получено, исходный Booster сохранён.

`train.py`, `evaluate.py`, `baseline.py` оставлены для воспроизводимости. `evaluate.py` проверяет временную границу модели; явный `--allow-in-sample` помечает результат диагностическим. Небезопасный legacy-split обучения отключён. Новую модель следует обучать в отдельный каталог и продвигать только после независимого подтверждения. Подробные параметры CLI: `python train.py --help`, `python evaluate.py --help`, `python baseline.py --help`.

## 7. Известные ограничения

- Покрытие — наблюдаемые пары sales. На полном train: 8 777 пар × 64 = 561 728 строк; число ТЗ 562 496 соответствует 11 × 799 декартовым парам. Уточнения судей этот конфликт не разрешили; скрытого дополнения пар нет. В 180-дневном входе ассортимент может быть меньше полного исторического.
- Кэш один на процесс и содержит последний успешный POST. Перезапуск его очищает. API рассчитан на последовательный демонстрационный сценарий; истории прогонов, изоляции пользователей и очереди заданий нет.
- Отдельных эндпоинтов каталога/истории и браузерного интерфейса пока нет. Для MVP нужен тонкий слой подготовки данных для графика и выбора пары.
- Два временных окна не доказывают устойчивость на всех сезонах. Занижение суммарного объёма остаётся проблемой: на подтверждении около −47,25%. SMAPE нельзя интерпретировать как «100% минус ошибка = точность».
- Семантика конфликтующих остатков не описана, поэтому сохраняется max. Отсутствующие финансовые/габаритные поля не восстанавливаются вымышленными значениями.
