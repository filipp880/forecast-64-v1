# Forecast Container — прогноз продаж по складам и товарам

Сервис из задания со звёздочкой (`Nonton_Backend_TZ_Forecasting_API`): HTTP-API на FastAPI
для прогноза `quantity` на 64 календарных дня вперёд по парам «склад × артикул».

> Статус: `Dockerfile`, `.dockerignore` и `docker-compose.yml` в репозитории. Перед
> сборкой образа обучите модель (`train.py`), иначе контейнер поднимется, но
> `POST /predict` будет отвечать `503 MODEL_NOT_READY`.

## 1. Описание решения

- **Модель:** по умолчанию один градиентный бустинг на **CatBoost** (`CatBoostRegressor`,
  таргет `log1p(quantity)`, нативные категориальные признаки). Это осознанно простая
  база: hurdle-модель (классификатор «будет ли продажа» + гейт), ансамбли и калибровка
  под SMAPE/Bias — следующие шаги. Тип модели — точка расширения: адаптеры живут в
  `app/models/` за общим интерфейсом `BaseForecastModel`, выбор — флагом
  `--model-type` при обучении и полем `model_type` в `config.json` (см. «Как заменить
  или добавить модель»).
- **Признаки** (модуль `app/features.py`, общий для обучения и инференса):
  - календарь целевого дня: `h` (горизонт 1..64), день недели, месяц, день, неделя года, выходной;
  - статистика серии по состоянию на дату отсечки: средние за 7/14/28/56/90 дней,
    доля нулей за 28/90 дней, последнее значение, дней с последней продажи,
    тренд `mean_28/mean_90`, число продажных дней за 90 дней, профиль по дню недели;
  - остатки: последний остаток, средний за 28 дней, доля нулей за 90 дней,
    запас покрытия `stock / mean_28`;
  - категориальные: `warehouse_name`, `article`, `category_lvl_1..3`, `characteristic`;
  - продажи агрегируются по департаментам/городам (ТЗ: суммируются в паре «склад × товар»).
- **Ключевое требование сценария с контейнером:** все признаки считаются по истории
  не глубже **180 дней** до даты отсечки — ровно столько данных приходит через API,
  поэтому одна и та же модель работает и на обучении, и в сервисе.
- **Инференс:** срез последних 180 дней → признаки на 64 дня вперёд → `expm1` → клиппинг
  в `[0, ∞)` → кэш. GET-эндпоинты отдают нарезки из кэша.
- **Детерминизм:** фиксированные `random_seed` и `thread_count`, обучение на CPU;
  повторный запуск на тех же данных даёт тот же прогноз.

Обучающий скрипт: `train.py` (подробности — «Обучение модели»). Пока модель не обучена,
`/health` и валидация работают, а `POST /predict` возвращает `503 MODEL_NOT_READY`.

## 2. Сборка (Docker)

База — `python:3.11-slim`. Сборка из директории `forecast-container/`:

```bash
docker build -t forecast-api .
```

Файл обученной модели `model/model.cbm` (имя берётся из `config.json`) попадает
в образ на момент сборки, поэтому обучите модель заранее
(`python train.py ...` — см. «Запуск»); без неё контейнер стартует, но `POST /predict`
вернёт `503 MODEL_NOT_READY`.

Требования: Docker ≥ 24, GPU не обязателен (обучение и инференс на CPU).
Ограничения ТЗ: сборка ≤ 60 мин, образ ≤ 30 GB, RAM ≤ 64 GB.

## 3. Запуск

Локально (Python 3.10+):

```bash
cd forecast-container
pip install -r requirements.txt
python train.py --sales ../data/sales_dataset_hakaton_train.csv \
                --stock ../data/stock_dataset_hakaton_train.csv \
                --out-dir model
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Запуск контейнера:

```bash
docker run -p 8000:8000 forecast-api
# или одной командой через compose:
docker compose up --build
```

Перед тестами API нужны сэмплы с историей ≥180 дней:

```bash
python scripts/make_samples.py
bash tests/test_api.sh
```

## 4. API

| Эндпоинт | Вход | Выход |
|---|---|---|
| `GET /health` | — | `{"status": "ok", "model_loaded": true}` |
| `POST /predict` | multipart: `sales`, `stock` (CSV, ≥180 дней истории) | `text/csv`, прогноз на 64 дня (562 496 строк на полных данных) |
| `GET /predict?article=&warehouse=` | хотя бы один из параметров | `text/csv`, срез кэша (нужен предварительный POST) |
| `GET /predict/all?format=csv\|json` | `format` (по умолчанию `csv`) | весь прогноз целиком |

Валидация POST: обязательные колонки, даты `YYYY-MM-DD`, история ≥180 дней (иначе `422`),
отрицательные `quantity`/`stock` (иначе `422`), пустой файл/ошибка парсинга (`400`).
Формат ошибок: `{"detail": "...", "code": "VALIDATION_ERROR"}`.

Браузерные клиенты: CORS открыт — по умолчанию все origins, список разрешённых
задаётся переменной окружения `CORS_ORIGINS` (через запятую, например
`http://localhost:5173`).

```bash
# Полный прогноз по загруженным данным
curl -X POST http://localhost:8000/predict \
  -F "sales=@data/sample_sales_6mo.csv" \
  -F "stock=@data/sample_stock_6mo.csv" \
  -o forecast.csv

# Прогноз по артикулу / складу / паре
curl "http://localhost:8000/predict?article=char_article_0" -o article_forecast.csv
curl "http://localhost:8000/predict?warehouse=warehouse_name_0" -o warehouse_forecast.csv
curl "http://localhost:8000/predict?article=char_article_0&warehouse=warehouse_name_0" -o pair_forecast.csv

# Весь прогноз
curl "http://localhost:8000/predict/all?format=csv" -o full_forecast.csv
curl "http://localhost:8000/predict/all?format=json" -o full_forecast.json
```

## 5. Структура репозитория

(`Dockerfile`, `docker-compose.yml`, `requirements.txt`, `README.md`,
`app/{main,predictor,validators}.py`, `model/*`, `data/sample_*.csv`,
`tests/test_api.sh`). Сверх минимума ТЗ: `train.py` и `evaluate.py` (обучение и
бэктест), `app/features.py` и `app/metrics.py`, `app/models/` (архитектура

### Обучение модели

```bash
cd forecast-container
python train.py                                    # catboost, значения по умолчанию: ../data/... и model/
python train.py --max-cutoffs 4 --model-params '{"iterations": 300}'  # быстрая проба
```

Схема — строгий holdout по времени (защита от утечки):

1. **Обучающие срезы** — только те, чьи таргеты заканчиваются до окна отбора:
   сетка срезов каждые `--cutoff-step` дней (по умолчанию 28), признаки строго
   «на дату среза» (история ≤ 180 дней).
2. **Early stopping** — на окне отбора: предпоследние 64 дня данных.
3. **Пять метрик ТЗ** — на тестовом окне: последние 64 дня, которых ранняя
   остановка не видела; метрики сохраняются в `model/config.json`
   (`validation.metrics`, `validation.early_stopping`).
4. **Финальный refit** — модель «в бой» переобучается на всех срезах (включая
   последние дни) с зафиксированным числом итераций из шага 2; отключается
   флагом `--no-refit`.

Модель выбирается флагом `--model-type` (параметры — `--model-params` JSON поверх
значений по умолчанию). В `model/` записываются три файла: сама модель
(`model.cbm`), `preprocessor.pkl` (спецификация пайплайна предобработки —
`predictor` сверяет её при загрузке) и `config.json`. При малом объёме данных
скрипт сам откатывается к простой схеме (train = все срезы кроме последнего).

**Журнал экспериментов.** Каждый прогон дописывает строку в `experiments.csv`
(метка `--tag "что меняли"`, параметры, число итераций, все пять метрик,
длительность) — сравнение вариантов по нему:

```bash
python train.py --max-cutoffs 4 --model-params '{"iterations": 500}' --no-refit \
    --tag "база (быстрый протокол)" --out-dir model_exp
```

Рекомендуемая лестница проверки изменений: **быстрый протокол** (~5–15 мин:
`--max-cutoffs 4 --no-refit`, сравнение по дельте метрик с базой)
→ **средний** (все срезы, `--no-refit`, ~30–60 мин — для сомнительных случаев)
→ **полный прогон** для финальной модели. Отключить журнал — `--no-log`.

### Как заменить или добавить модель

Весь код обучения/инференса работает через интерфейс `BaseForecastModel`
(`app/models/base.py`), поэтому замена модели — это один флаг `--model-type`,
а добавление новой — один новый класс:

1. Создайте класс-наследник `BaseForecastModel` в `app/models/` (пример:
   `catboost_model.py`) и реализуйте `fit` / `predict` /
   `save` / `load`; объявите `name`, `file_suffix` и `default_params()`.
   Если у модели есть свои требования к признакам (кодирование категориальных
   и т.п.) — инкапсулируйте их внутри класса: контракт `fit`/`predict` не меняется,
   `train.py` и `predictor.py` о деталях не знают.
2. Зарегистрируйте класс в `MODEL_REGISTRY` (`app/models/__init__.py`).
3. При необходимости добавьте библиотеку в `requirements.txt` и пересоберите образ.
4. Обучите: `python train.py --model-type <имя>`. Инференс подхватит новую модель
   автоматически — тип читается из `config.json`.

Категориальные признаки: catboost принимает строки нативно. Если новая модель строк
не принимает (например, sklearn), её кодирование (`OrdinalEncoder` и т.п.) и обучение
энкодера инкапсулируются в классе модели — интерфейс `fit`/`predict` и остальной код
не меняются. Трансформ таргета — атрибут класса `target_transform` (по умолчанию `log1p`).

### Проверка качества модели

ТЗ оценивает прогноз по пяти метрикам: **SMAPE (50%), WAPE (20%), RMSE (15%),
|Bias| (10%), RMSLE (5%)**. Реализация 1-в-1 по формулам ТЗ (п. 5.2, включая
краевые случаи SMAPE и исключение серий с нулевым средним из Bias) — в
`app/metrics.py`.

- `train.py` в конце печатает все пять метрик на тестовом окне (последние 64 дня,
  которых не видела ранняя остановка) и сохраняет их в `model/config.json` →
  `validation` (схема, срезы отбора/теста, горизонт, строки, метрики, число
  итераций) — «карточка модели» для сравнения запусков.
- `evaluate.py` — честный бэктест: берёт несколько последних **полных** срезов,
  считает для каждого прогноз по данным «до среза» и выводит метрики по каждому
  срезу, среднее и разбивку по горизонтам 1–7 / 8–28 / 29–64 дней:

```bash
python evaluate.py                                             # 8 последних полных срезов, шаг 28 дней
python evaluate.py --max-cutoffs 4 --cutoff-step 56            # быстрее
python evaluate.py --out report.json                           # сохранить JSON-отчёт
```

Нюанс: по умолчанию финальная модель дообучается на всех срезах (`--refit`), поэтому
исторические срезы `evaluate.py` были и в её обучении — метрики оптимистичны
(честная вневыборочная оценка — `validation` из `train.py`). Для бэктеста
«как на соревновании» обучите с `--no-refit` — модель будет знать только срезы
до окна отбора — и прогоните `evaluate.py` по последним полным срезам.

## 6. Известные ограничения

- Файла модели в репозитории нет — её нужно обучить скриптом `train.py`
  (до этого `POST /predict` отвечает `503 MODEL_NOT_READY`, GET-эндпоинты — `400`).
- В данных организаторов нет `cost_price` и `volume_weight` (см. `data/нюансы.txt`) —
  валидатор их не требует; они принимаются, если присутствуют.
- Колонка остатков приходит как `article` в текущей выгрузке (в ТЗ — `char_article`);
  валидатор и панель принимают оба имени.
- Отрицательный `stock` в выгрузке встречается (≈57 строк во всём train): POST его
  отклоняет по ТЗ (`422`), а при обучении панель клиппит такие значения в 0 —
  модель учится в том же пространстве, в котором работает на инференсе.
- В train-выборке фактически 8777 пар «склад × товар» (11 × 799 полной сетки, но 12 пар
  не встречаются), поэтому прогноз строится по парам из переданных данных.
- `GET /predict/all?format=json` на полных данных — сотни мегабайт; рекомендуется `csv`
  (отдаётся потоково). GET-эндпоинты без предшествующего POST возвращают `400`.
- Оценка в `train.py` — одно 64-дневное окно отбора и одно тестовое (честные, но
  одиночные). Более устойчивая картина — `evaluate.py` (бэктест по нескольким
  полным срезам с разбивкой по горизонтам), с поправкой на перекрытие с обучением
  (см. «Проверка качества модели»).
