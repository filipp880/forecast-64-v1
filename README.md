# Прогноз недельных продаж на 9 недель

## 1. Описание решения

Глобальная модель прогнозирует сумму `quantity` за неделю для пары `warehouse_name × article`. Обученные веса находятся в `model/`; переобучение для запуска API не требуется.

Текущая модель использует LightGBM и маршрутизацию по прошлому среднему спросу. Основа — ансамбль 0,3 × hurdle + 0,7 × регрессия `log1p(quantity)` (120/188/88 деревьев). Для спроса менее 0,5 единицы в неделю используется MAE-регрессор; для 0,5–2 — модель распределения quantity с lambda=3; для 2–10 — dynamics с порогом 0,6; для 10–50 — смесь 50% recent-MAE эксперта и 50% основы с сохранением нулей основы; для 50+ — смесь 50% SBA и 50% основы с сохранением её маски. Все границы определяются только по прошлым 28 дням, без будущего факта.

Count и recent-MAE эксперты используют 102 признака, включая 13 недельных лагов с явными masks неизвестной истории; препроцессор формирует 121 доступную колонку. MAE для редких рядов использует 68 признаков, включая прошлые денежные агрегаты и календарь; dynamics — 49. Допустимы дробные прогнозы; итог не округляется повторно после смешивания экспертов. Схема preprocessing v7 защищает загрузку новыми весами несовместимого старого runtime.

Продажи суммируются через города и департаменты. Дубли остатков внутри дня суммируются, отрицательные остатки сохраняются. Будущие продажи и остатки не используются.

Средние показатели на исторических окнах с отсечками 18.01 и 22.03.2026, которые участвовали в выборе текущего рецепта:

| SMAPE | WAPE | RMSE | Средний абсолютный Bias по сериям | RMSLE |
|---:|---:|---:|---:|---:|
| 61,6637% | 48,3270% | 2,5676 | 74,0485% | 0,5195 |

Это ретроспективный выбор по общему локальному ранговому Score с весами 50/20/15/10/5 среди 1 797 недельных конфигураций на двух одинаковых окнах. Score выбранной комбинации — 0,155526, предыдущего релиза — 0,193179; меньше лучше. Значения зависят от состава локальных кандидатов и не равны баллам закрытого лидерборда. Независимого подтверждения и полной майской оценки этого рецепта нет. На июльских данных обучены недостающие MAE-модели, использованы 1 160 298 строк из 16 разрешённых отсечек; dynamics и count сохранены из идентичного полного обучения. Готовый прогноз — **[forecast.csv](forecast.csv)**. Параметры и SHA-256 — [forecast.manifest.json](forecast.manifest.json), полный состав пар — [required_pairs.csv](required_pairs.csv). Исторически наблюдавшиеся пары перечислены отдельно в `observed_pairs.csv`.

Готовый CSV содержит **79 101 строку: 11 складов × 799 артикулов × 9 недель**. Для 12 пар без истории используется fallback по среднему спросу артикула за последние 28 дней; для наблюдавшихся пар используются текущие веса и описанная маршрутизация. Для повторной генерации полного набора: `python generate_submission.py --all-combinations --out forecast_new.csv`.

Новый запуск создаёт собственный комплект `forecast_new.csv`, `forecast_new.pairs.csv`, `forecast_new.manifest.json`. Существующие файлы комплекта защищены от перезаписи без `--overwrite`; входные файлы нельзя использовать как выходные. Переданный `--required-pairs` проверяет локальное совпадение ключей и не означает подтверждения каталога организатором. Групповые признаки наблюдавшихся пар вычисляются одинаково при любом запрошенном каталоге.

Обучение реализовано в `train.py`; расширенный research-тип поддерживает expert_specs из model/config.json. Исследования SMAPE/WAPE находятся в `research_count_distribution.py`, `research_regular_quantity.py`, `select_smape_wape_joint.py` и `adaptive_smape_wape_cv.py`. Текущий финальный refit реализован в `finalize_rank_release.py` и требует локальных проверенных OOF-кэшей и выбранного рецепта. Полные исходные CSV и кэши размещаются локально и не входят в Git/образ. Для воспроизведения старого замороженного запуска нужен его baseline и snapshot исходников; смена текущего champion намеренно блокирует незаметный resume.

Базовый research_weekly.py ограничен исходными профилями и не подменяет специализированный цикл count/MAE экспертов. Протоколы сохраняют рецепт и SHA baseline, обучают модели только на доступном прошлом origin; старые каталоги не редактируются для обхода проверки исходников. Текущая selection явно помечена как адаптивная, включая уже просмотренный май.

Предшествующие ограниченные исследования реализованы в `scripts/research_decision.py`, `research_events.py`, `research_magnitude.py`, `research_cold_pairs.py` и `research_reconciliation.py`. Они требуют локальных OOF-кэшей в `artifacts/` и не входят в runtime. Текущий рецепт выбран повторным сравнением сохранённых недельных результатов по общему Score.

## 2. Инструкция по сборке

Требуется Docker Engine с Linux-контейнерами. Используется Python 3.11, зависимости закреплены в `requirements.lock.txt`. GPU не нужен. Интернет требуется при первой сборке. Все команды выполняются из корня репозитория:

```bash
docker build -t forecast-api .
```

`.dockerignore` исключает полные данные, локальные артефакты, кэши и секреты. В образ включены код приложения и готовая модель.

## 3. Инструкция по запуску

```bash
docker run --rm --name forecast-api -p 127.0.0.1:8000:8000 forecast-api
```

Альтернатива: `docker compose up --build`. Swagger: http://localhost:8000/docs. Готовность: http://localhost:8000/ready (200 при загруженной модели, иначе 503). `/health` проверяет живость процесса и показывает `model_loaded`. Docker healthcheck использует `/ready`.

Parsing, валидация и прогноз выполняются вне event loop. По умолчанию допускается один тяжёлый POST одновременно; `MAX_CONCURRENT_PREDICTIONS` задаёт положительное число таких запросов на процесс. Остальные POST ожидают очередь; `/health`, `/ready` и чтение последнего готового прогноза продолжают обслуживаться. Кэш принадлежит одному процессу, поэтому несколько независимых workers требуют отдельного решения хранения кэша.

Модель работает автономно. Для запуска с отключённой сетью доступен `docker run --rm --network none forecast-api`; публикация порта хоста в таком режиме недоступна. CUDA-флаги не требуются.

## 4. Описание API

| Метод | Путь | Результат |
|---|---|---|
| GET | `/health` | состояние загрузки модели |
| GET | `/ready` | готовность модели, 200 или 503 |
| POST | `/predict` | полный прогноз по двум multipart-файлам |
| GET | `/predict?article=…` | CSV по артикулу |
| GET | `/predict?warehouse=…` | CSV по складу |
| GET | `/predict?article=…&warehouse=…` | CSV пары |
| GET | `/predict/all?format=csv` | весь последний прогноз |
| GET | `/predict/all?format=json` | тот же прогноз в JSON |

```bash
curl -f http://localhost:8000/health
curl -f -X POST http://localhost:8000/predict \
  -F "sales=@data/sample_sales_6mo.csv" \
  -F "stock=@data/sample_stock_6mo.csv" -o forecast_result.csv
curl -f "http://localhost:8000/predict?article=char_article_0" -o article_result.csv
curl -f "http://localhost:8000/predict?warehouse=warehouse_name_0" -o warehouse_result.csv
curl -f "http://localhost:8000/predict?article=char_article_0&warehouse=warehouse_name_0" -o pair_result.csv
curl -f "http://localhost:8000/predict/all?format=csv" -o full_result.csv
curl -f "http://localhost:8000/predict/all?format=json" -o forecast_result.json
```

sales: `date,composite_division,cities_name,warehouse_name,category_lvl_1,category_lvl_2,category_lvl_3,article,characteristic,quantity,sales_sum,discount_sum`.

stock: `date,warehouse_name,char_article,stock`. Пустая скидка допустима. В обоих файлах требуется минимум 180 календарных дней; более длинная история учитывается целиком.

Выход: `week,warehouse_name,article,quantity`. API формирует полное произведение складов и артикулов входных sales, включая пары без совместной истории с fallback. Прогноз начинается с понедельника следующей календарной недели после максимальной даты sales и содержит девять полных недель. Например, после 31.07.2026 первая неделя — 03.08.2026. Quantity — неотрицательное конечное число, сумма за полную неделю. GET читает кэш последнего успешного POST; до POST кэш отсутствует. Неверная схема/глубина истории — 422, отсутствие GET-фильтра или ещё не рассчитанный прогноз — 400.

`sample_sales.csv` и `sample_stock.csv` содержат первые 100 строк для ознакомления со схемой. Для POST предназначены `sample_*_6mo.csv`.

Проверка кода и готового комплекта из корня проекта:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scripts/verify_release.py
```

Pytest собирает только `tests/`, исключая локальные архивы. В проверках есть настоящий инференс приложенных весов и небольшое обучение/сохранение/оценка расширенных семейств `research` и `ideas`. `verify_release.py` сверяет CSV, каталог, модель, временное происхождение и SHA; закрытое внешнее множество ключей эта проверка не подтверждает.

Локальный архив исходников, samples, весов и готового прогноза собирается командой `python scripts/package_release.py --out artifacts/release.zip`. Он содержит `RELEASE_MANIFEST.json` с SHA всех включённых файлов; полные train CSV, локальные отчёты и кэши в архив не включаются. Существующий архив не перезаписывается.

Текущие веса проверены полным HTTP-инференсом в Linux/Docker/Python 3.11 с `--network none`, 6 CPU и лимитом 7 GiB RAM. Два POST дали 79 101 строку за 45,31 и 43,73 секунды; повторные байты одинаковы, значения совпадают с CSV. GET CSV/JSON и фильтры согласованы. Пик памяти контейнера — около 3,41 GiB. Эти ресурсные показатели относятся к данному входному набору.

## 6. Известные ограничения

- Состав 79 101 ключей восстановлен полным произведением 11 × 799 × 9 согласно ожидаемой размерности внешней проверки. Машиночитаемый эталон не предоставлен; точное совпадение ключей должен подтвердить повторный внешний прогон.
- Готовый прогноз использует историю только по 26.07.2026 и охватывает 27.07–27.09.2026; последняя метка week — 21.09.2026. API использует даты загруженных данных.
- Календарные признаки используются MAE-веткой для редких рядов; региональная привязка анонимных складов неизвестна. Будущие акции и остатки модели не предоставляются.
- Кэш находится в памяти одного процесса и очищается при перезапуске. Отдельный пользовательский веб-интерфейс не предусмотрен.
