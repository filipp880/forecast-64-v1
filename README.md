# Прогноз недельных продаж на 9 недель

Модель прогнозирует недельные продажи на девять недель вперёд. В репозитории находятся обученные веса, готовый CSV и автономный HTTP API.

| Файл | Назначение |
|---|---|
| [forecast.csv](forecast.csv) | Готовый прогноз на 9 недель, 79 101 строка |
| [model/config.json](model/config.json) | Архитектура, параметры и схема признаков |
| [model/model.pkl](model/model.pkl) | Обученные веса |
| [model/preprocessor.pkl](model/preprocessor.pkl) | Схема подготовки признаков |
| [required_pairs.csv](required_pairs.csv) | Каталог 8 789 прогнозируемых пар |
| [forecast.manifest.json](forecast.manifest.json) | Происхождение прогноза и контрольные суммы |

Обучение использует историю **по 26.07.2026 включительно**. Прогноз охватывает **27.07–27.09.2026**; последняя метка `week` — `2026-09-21`. Для запуска API переобучение не требуется.

## 1. Описание решения

Глобальная модель прогнозирует сумму `quantity` за неделю для пары `warehouse_name × article`. Обученные веса находятся в `model/`; переобучение для запуска API не требуется.

Текущая модель смешивает два варианта LightGBM: **75% ветви с уточнённой count-моделью + 25% основы с обновлённым числом итераций**, затем округляет результат. В первой ветви count-модель заменяет прогноз для прошлого среднего спроса от 0,5 до 10 единиц в неделю; вне этого диапазона используется сохранённая исходная основа. Вторая ветвь использует обновлённые шесть компонентов исходного рецепта.

Внутренняя основа сочетает 0,3 × hurdle и 0,7 × регрессию `log1p(quantity)` со специализацией экспертов по спросу. Средний недельный спрос для выбора ветки равен `mean_28 × 7` и рассчитывается только по прошлым 28 дням. Внутренние правила основы:

| Средний спрос, единиц в неделю | Правило прогноза |
|---|---|
| Менее 0,5 | MAE-регрессор с округлением |
| От 0,5 до 2 | Модель распределения количества, lambda=3 |
| От 2 до 10 | Dynamics с порогом 0,6 |
| От 10 до 50 | 50% recent-MAE + 50% основы, нули основы сохраняются |
| От 50 | 50% SBA + 50% основы, маска нулевых/положительных прогнозов основы сохраняется |

Правая граница каждого интервала исключается; точные правила смешивания и округления задаёт рецепт в `model/config.json`.

Уточнённая count-модель использует 13 классов количества и 209 признаков: недельные лаги, историю до 52 недель с обработкой неизвестных наблюдений, доступность товара, сезонные и групповые признаки. Внутренние count и recent-MAE эксперты используют 102 признака и 13 недельных лагов; MAE для редких рядов — 68, dynamics — 49. Итоговый прогноз после смешивания округляется через `np.rint`. Схема preprocessing v8 защищает загрузку весов несовместимым старым runtime. Признаки рассчитываются только из данных текущего запроса; папки экспериментов и локальные train CSV для работы API не нужны.

Продажи суммируются через города и департаменты. Дубли остатков внутри дня суммируются, отрицательные остатки сохраняются. Будущие продажи и остатки не используются.

Финальные веса используют **1 160 298 обучающих строк из 16 исторических отсечек**, с целями не позднее 26.07.2026; специалисты по положительным продажам и регулярному спросу обучаются на соответствующих подмножествах. Новые компоненты используют 124 итерации уточнённой count-модели, 218/296/201 итерацию классификатора, положительного регрессора и log-регрессора; MAE — 350, внутренний count — 145, recent-MAE — 229. Для многоклассовых моделей число деревьев равно числу итераций, умноженному на количество классов. Исторически наблюдавшиеся пары перечислены отдельно в [observed_pairs.csv](observed_pairs.csv).

Готовый CSV содержит **79 101 строку: 11 складов × 799 артикулов × 9 недель**. Для 12 пар без истории используется fallback по среднему спросу артикула за последние 28 дней; для наблюдавшихся пар используются текущие веса и описанная маршрутизация. Для повторной генерации полного набора: `python generate_submission.py --all-combinations --out forecast_new.csv`.

Новый запуск создаёт собственный комплект `forecast_new.csv`, `forecast_new.pairs.csv`, `forecast_new.manifest.json`. Существующие файлы комплекта защищены от перезаписи без `--overwrite`; входные файлы нельзя использовать как выходные. Через `--required-pairs required_pairs.csv` можно задать точный каталог пар. Групповые признаки наблюдавшихся пар вычисляются одинаково при любом запрошенном каталоге.

Обучение реализовано в [train.py](train.py); тип модели `research` поддерживает `expert_specs` из `model/config.json`. Финальная сборка весов реализована в [scripts/finalize_rank_release.py](scripts/finalize_rank_release.py) и требует локальных обучающих кэшей и файла рецепта. Полные исходные CSV и кэши хранятся локально и не входят в Git или Docker-образ.

## 2. Инструкция по сборке

Требуется Docker Engine с Linux-контейнерами. Используется Python 3.11, зависимости закреплены в `requirements.lock.txt`. GPU не нужен. Интернет требуется при первой сборке. Все команды выполняются из корня репозитория:

```bash
docker build -t forecast-api .
```

`.dockerignore` исключает полные данные, локальные артефакты, кэши и секреты. В образ включены код приложения и готовая модель.

## 3. Инструкция по запуску

```bash
docker run --rm --name forecast-api -p 127.0.0.1:8000:8000 forecast-api
```

Альтернатива: `docker compose up --build`. Swagger: http://localhost:8000/docs. Готовность: http://localhost:8000/ready (200 при загруженной модели, иначе 503). `/health` проверяет живость процесса и показывает `model_loaded`. Docker healthcheck использует `/ready`.

Parsing, валидация и прогноз выполняются вне event loop. По умолчанию допускается один тяжёлый POST одновременно; `MAX_CONCURRENT_PREDICTIONS` задаёт положительное число таких запросов на процесс. Остальные POST ожидают очередь; `/health`, `/ready` и чтение последнего готового прогноза продолжают обслуживаться. Кэш принадлежит одному процессу, поэтому несколько независимых workers требуют отдельного решения хранения кэша.

Модель работает автономно. Для запуска с отключённой сетью доступен `docker run --rm --network none forecast-api`; публикация порта хоста в таком режиме недоступна. CUDA-флаги не требуются.

## 4. Описание API

| Метод | Путь | Результат |
|---|---|---|
| GET | `/health` | состояние загрузки модели |
| GET | `/ready` | готовность модели, 200 или 503 |
| POST | `/predict` | полный прогноз по двум multipart-файлам |
| GET | `/predict?article=…` | CSV по артикулу |
| GET | `/predict?warehouse=…` | CSV по складу |
| GET | `/predict?article=…&warehouse=…` | CSV пары |
| GET | `/predict/all?format=csv` | весь последний прогноз |
| GET | `/predict/all?format=json` | тот же прогноз в JSON |

```bash
curl -f http://localhost:8000/health
curl -f -X POST http://localhost:8000/predict \
  -F "sales=@data/sample_sales_6mo.csv" \
  -F "stock=@data/sample_stock_6mo.csv" -o forecast_result.csv
curl -f "http://localhost:8000/predict?article=char_article_0" -o article_result.csv
curl -f "http://localhost:8000/predict?warehouse=warehouse_name_0" -o warehouse_result.csv
curl -f "http://localhost:8000/predict?article=char_article_0&warehouse=warehouse_name_0" -o pair_result.csv
curl -f "http://localhost:8000/predict/all?format=csv" -o full_result.csv
curl -f "http://localhost:8000/predict/all?format=json" -o forecast_result.json
```

sales: `date,composite_division,cities_name,warehouse_name,category_lvl_1,category_lvl_2,category_lvl_3,article,characteristic,quantity,sales_sum,discount_sum`.

stock: `date,warehouse_name,char_article,stock`. Пустая скидка допустима. В обоих файлах требуется минимум 180 календарных дней; более длинная история учитывается целиком.

Выход: `week,warehouse_name,article,quantity`. API формирует полное произведение складов и артикулов входных sales, включая пары без совместной истории с fallback. Прогноз начинается с понедельника следующей календарной недели после максимальной даты sales и содержит девять полных недель. Например, после 31.07.2026 первая неделя — 03.08.2026. Quantity — неотрицательное конечное число, сумма за полную неделю. GET читает кэш последнего успешного POST; до POST кэш отсутствует. Неверная схема/глубина истории — 422, отсутствие GET-фильтра или ещё не рассчитанный прогноз — 400.

`sample_sales.csv` и `sample_stock.csv` содержат первые 100 строк для ознакомления со схемой. Для POST предназначены `sample_*_6mo.csv`.

Проверка кода и готового комплекта из корня проекта:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scripts/verify_release.py
```

Pytest собирает только `tests/`, исключая локальные архивы. В проверках есть инференс приложенных весов и обучение/сохранение/оценка семейств `research` и `ideas`. `verify_release.py` сверяет CSV с приложенным каталогом, моделью, датами истории и SHA.

Локальный архив исходников, samples, весов и готового прогноза собирается командой `python scripts/package_release.py --out artifacts/release.zip`. Он содержит `RELEASE_MANIFEST.json` с SHA всех включённых файлов; полные train CSV, локальные отчёты и кэши в архив не включаются. Существующий архив не перезаписывается.

Текущие веса проверены полным HTTP-инференсом в Linux/Docker/Python 3.11 с `--network none`, 6 CPU и лимитом 7 GiB RAM. Два POST дали 79 101 строку за 53,85 и 54,06 секунды; повторные байты одинаковы, значения совпадают с CSV. GET CSV/JSON и фильтры согласованы. Пик памяти контейнера, включая клиент проверки, — около 3,66 GiB. Эти ресурсные показатели относятся к данному входному набору.

## 6. Известные ограничения

- По умолчанию формируется полное произведение складов и артикулов из входных продаж. Если нужен другой состав пар, задайте явный каталог через `--required-pairs` при генерации CSV.
- Готовый прогноз использует историю только по 26.07.2026 и охватывает 27.07–27.09.2026; последняя метка week — 21.09.2026. API использует даты загруженных данных.
- Календарные признаки используются уточнённой count-моделью и MAE-веткой для редких рядов; региональная привязка анонимных складов неизвестна. Будущие акции и остатки модели не предоставляются.
- Кэш находится в памяти одного процесса и очищается при перезапуске. Отдельный пользовательский веб-интерфейс не предусмотрен.
