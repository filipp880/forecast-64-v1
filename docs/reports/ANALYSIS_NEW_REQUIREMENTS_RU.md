## 1. Главный вывод

Нынешний сервис — пригодная инженерная основа, но текущий прогноз и сохранённые веса не подходят для сдачи по обновлённому ТЗ. ## 4. P0: обязательные изменения до нового submission

### 4.1. Исключить утечку за пределы 26 июля

Где: `forecast-container/train.py:362`, `generate_submission.py:22`, `model/config.json:89`.

Сейчас CSV читаются целиком, а сохранённый config объявляет training_data_end=2026-07-31. Для нового соревнования такой комплект нельзя использовать как итоговую модель.

Нужно:

- Ввести явный history_cutoff для основного соревнования — 2026-07-26.
- Обрезать sales И stock до этой даты до построения панели, категорий, признаков и обучения. Эталонный каталог пар подключать отдельно.
- Не использовать 27–31 июля для выбора параметров, early stopping и калибровки основного решения.
- Проверять происхождение артефакта: даты обучения и отбора должны укладываться в допустимую границу.
- Переобучить обе части blend, то есть все три бустера. Изменение даты в config не удаляет информацию из весов.
- Сохранить новую модель в отдельном каталоге; обновить model.pkl, preprocessor.pkl, config.json и их хеши согласованно.

### 4.2. Ввести недельный календарь и недельный target

Где: `app/features.py:51`, `:255`, `:296`; `app/predictor.py:181`; `train.py:340`; `app/submission.py:5`.

Сегодня h означает число дней после cutoff, а target — продажи одного дня. Замена HORIZON=64 на HORIZON=9 создаст девять дневных прогнозов.

Рекомендуемая новая схема: forecast_weeks=9, h_week=1..9, отдельные history_cutoff и first_week. Обучающий target — сумма quantity за семь дней целевой недели, после агрегации департаментов/городов. Признаки доступны только на origin. Неполные недели в конце истории не должны превращаться в полные недельные target с искусственными нулями.

Сам алгоритм LightGBM/CatBoost/ансамбля менять обязательно не требуется; требуется изменить данные задачи и переобучить его.

### 4.3. Исправить остатки

Где: `app/features.py:82`, `:91`; описание `app/validators.py:3`.

Сейчас отрицательный stock обнуляется через clip, затем дубли агрегируются max. Новое правило: исходный signed stock сохраняется, дубли суммируются по date + warehouse_name + article. Например, +5 и −2 дают 3.

Суммирование обязательно внутри одного дня. Остатки разных дней — состояния на начало дня: их недельная сумма не равнозначна объёму продаж/поставок. Для признаков использовать последний известный остаток, среднее/минимум, долю отрицательных дней, величину резерва. Это варианты признаков, а не обязательный перечень ТЗ. Производный days_of_cover определить явно с учётом резервов.

Не удалять продажи при stock=0 или stock<0 и не ограничивать прогноз механически текущим остатком.

Повысить PREPROCESSING_VERSION, зафиксировать stock_aggregation=sum и negative_stock_policy=preserve в спецификации. Старые веса не должны молча загружаться с новой семантикой признаков.

### 4.4. Переписать контракт и генератор CSV

Где: `app/submission.py:9`, `generate_submission.py:29`, `app/predictor.py:207`.

Валидатор должен принимать явные first_week, weeks=9 и expected_pairs, проверять точный набор ключей week + warehouse_name + article, понедельники и шаг 7 дней, отсутствие пропусков/дублей/лишних пар, числовые конечные неотрицательные quantity. Дробные quantity допустимы.

Существующая проверка только наблюдаемых sales-пар недостаточна для соревнования. Добавить вход required_pairs, например CSV каталога. Если эталон содержит пары без продаж, обеспечить прогноз/fallback для них; его качество проверять отдельно.

Генератор основного submission должен явно применять фиксированные даты. API должен вычислять даты динамически. Обоим нужен общий код построения прогноза и проверки результата, чтобы избежать двух расходящихся реализаций.

### 4.5. Исправить строгий скоринг и WAPE

Где: `app/metrics.py:39`, `:74`, `:117`.

Формулы SMAPE, Bias и RMSLE в основном уже соответствуют требованиям; веса 50/20/15/10/5 правильные. SMAPE учитывает 0/0 как нулевую ошибку внутри среднего, это нужно сохранить.

Обязательные исправления:

- Перейти с ключа date на week при оценке недельного результата.
- При суммарном нулевом факте WAPE должен быть 0 при нулевой ошибке и 100 при ненулевой; сейчас функция всегда возвращает 0.
- До merge строго проверить равенство ключей truth/prediction. Сейчас left merge теряет лишние ключи, отсутствующие прогнозы заполняются нулём, отрицательные клиппируются. Некорректный submission должен отклоняться, а не улучшаться таким исправлением.
- После успешной проверки считать метрики без скрытого заполнения/исправления прогноза.

В примере score.py из ТЗ внутри compute_all_metrics по-прежнему есть fillna/clip, хотя нормативный текст запрещает исправлять некорректный submission. Следовать строгой валидации из разделов 4 и 5.5, не переносить пример вслепую.

## 5. P1: обучение и доказательство качества

Дневные SMAPE≈29,59%, WAPE≈73,71% и volume_bias≈−47,25% из сохранённого отчёта не являются качеством недельного решения. Их сохранить как историю; новую модель выбирать по новым измерениям.

Переработать `train.py`, `evaluate.py`, `baseline.py`, `app/temporal.py`, `scripts/verified_backtest.py` и `scripts/select_candidate.py`:

- Выбрать origins и девять полных недель факта после каждого origin. Для основного сценария естественны воскресные origins; динамический API дополнительно проверить на остальных днях недели.
- Сохранить существующий принцип: оценочная копия обучается только на прошлом своего origin, подбор и контроль разделены по времени.
- Границы разделения считать по последнему дню target-недели, а не механически заменить дневной horizon на число 9.
- Не использовать факты 27–31 июля ни в одном этапе основного решения.
- В новых экспериментах убрать stock_policy=legacy; одинаковая исправленная предобработка должна работать в обучении, оценке и API.
- Построить недельные baseline: ноль, последняя полная неделя, средние нескольких полных недель.
- Считать все пять метрик на недельных суммах; показать ошибки по неделям 1–3 / 4–6 / 7–9, складам, частоте спроса и величине продаж.
- Переоценить gate=0.5, вес hurdle=0.3 и округление. Это параметры прежней задачи, не новые требования. ТЗ не требует целочисленного quantity.
- Не считать сумму сырых метрик итоговым score: нормализация обязательна. ТЗ ожидает ранговую версию, но локальный rank зависит от набора сравниваемых кандидатов и не является официальным местом на лидерборде.
- Создать новый протокол и каталог результатов. Уже просмотренные контрольные окна не выдавать за новое независимое подтверждение после повторной настройки.

Два технически допустимых подхода для сравнения:

1. Переобученная дневная модель с последующим суммированием в полные недели. Для API внутренний горизонт относительно max(sales.date) может достигать 69 дней: при последней дате в понедельник требуются h=7..69, при пятнице h=3..65. Старого горизонта 64 недостаточно. Обратное преобразование target выполняется до недельной суммы; округление/пороги необходимо проверить на недельной валидации.
2. Direct weekly модель: сразу прогнозирует недельную сумму, h_week=1..9. Это рекомендуемый основной кандидат, но преимущество над дневным адаптером нужно измерить.

ТЗ требует принимать и более длинную историю, чем 180 дней. Сейчас файлы целиком принимаются, но числовые исторические признаки ограничены lookback_days=180. При буквальном выполнении требования «по всем предоставленным данным» предусмотреть использование более длинной доступной истории, например длинных недельных агрегатов. Само наличие коротких rolling-окон не является ошибкой; при коротком API-входе модель должна сохранять работоспособность.

## 6. Финансовые поля и null

В боевой модели sales_sum/discount_sum не входят в FEATURE_COLUMNS. Новое ТЗ не обязывает вводить их в модель. Поэтому для соответствия не нужно экспоненцировать quantity или stock.

Собственное преобразование log1p(quantity) разрешено; ему соответствует expm1, как в текущем коде.

Если вводить денежные недельные признаки, известное исходное преобразование — np.log, значит сначала np.exp известных значений, затем сумма. Исходный null discount_sum даёт денежный вклад 0. Нельзя делать exp(fillna(0)): это превратит отсутствие скидки в 1. Не следует также считать любое числовое значение 0 в логарифмическом представлении пропуском.

В локальном игнорируемом `scripts/m5_lab.py:84` финансовые поля суммируются напрямую. При возвращении этого эксперимента в работу исправить преобразования прежде, чем сравнивать его с новой моделью.
