## 0. TL;DR (2 минуты, если некогда читать)

1. **Задача:** предсказать `quantity` на **64 дня вперёд** в разрезе `склад × артикул` (до 11 × 799 = 8 789 серий), итого **562 496 строк** в CSV.
2. **Метрика:** `Score = 0.50·SMAPE + 0.20·WAPE + 0.15·RMSE + 0.10·Bias + 0.05·RMSLE`, все метрики нормализуются (официально — **рангом**), **чем ниже, тем лучше**.
3. **Главная стратегия:** SMAPE (50% веса) считается **по каждой серии отдельно** и **штрафует на 200% за каждый день «факт>0, прогноз=0» и «факт=0, прогноз>0»**. Побеждает не «точная регрессия», а **правильное попадание в дни продаж**: ноль в непродажный день не наказывается, ложный плюс — наказывается максимально.
4. **Лучшая архитектура:** глобальная **hurdle-модель** = классификатор «будет ли продажа» (гейт по порогу) + регрессор «сколько, если будет» (CatBoost/LightGBM на `log1p`), обученные на всех сериях сразу, + пост-обработка (калибровка Bias, обнуление «спящих» серий) + ансамбль.
5. **Валидация:** держим последние 64 дня истории как псевдо-горизонт, фичи считаем строго «на дату отсечки» — никаких утечек.
6. **Со звёздочкой (Docker+FastAPI):** модель в контейнере получает **только 180 дней** истории → признаки надо делать **глубиной ≤180 дней**, иначе веса из основной модели не встанут в API-режим. Это главный подводный камень.

## 2. Разбор метрик: как это выигрывают (САМЫЙ ВАЖНЫЙ РАЗДЕЛ)

### 2.1 Точные правила из `score.py` (не по тексту ТЗ, а по коду)

| Метрика | Вес | Область усреднения | Формула (из кода) |
|---|---|---|---|
| SMAPE | **0.50** | **по каждой серии**, потом среднее по сериям | `\|y-ŷ\| / ((\|y\|+\|ŷ\|)/2) × 100`, среднее **только по дням, где знаменатель > 0** |
| WAPE | 0.20 | глобально (одно число) | `Σ\|y-ŷ\| / Σ\|y\| × 100` |
| RMSE | 0.15 | глобально | `sqrt(mean((y-ŷ)²))` |
| Bias | 0.10 | **по каждой серии** (серии с `mean(y)=0` исключаются!), потом среднее | `\|mean(ŷ) - mean(y)\| / mean(y) × 100` |
| RMSLE | 0.05 | глобально | `sqrt(mean((log1p(ŷ)-log1p(y))²))` |

Критические детали кода, которые **меняют стратегию**:

1. **Дни «факт=0, прогноз=0» исключаются из знаменателя SMAPE** (`mask = denominator > 0`). То есть за угаданный ноль **нет «кредита»**: SMAPE серии = среднее относительной ошибки только по дням, где «что-то случилось» (либо была продажа, либо модель ошибочно предсказала плюс).
2. Если серия **все 64 дня нулевая в факте и модель предсказала 0** → `mask.any() == False` → SMAPE серии = **0** (идеал). Если при этом модель предсказала хоть что-то → **200% за каждый день**.
3. **Пропуски строк в submission заполняются нулём** (`fillna(0)`) — то есть забытая строка = предсказание 0 = 200% SMAPE там, где была продажа. Плюс отрицательные значения клиппятся в 0.
4. Мерж идёт **left от truth**: лишние строки в submission игнорируются, **дубликаты ключей размножат строки** и исказят метрики → в `date×warehouse×article` должен быть ровно 1 уникальный ключ.
5. Валидатор формата **только предупреждает** (не падает): число строк, 64 даты подряд, число пар = 8 789.

### 2.2 Краевые случаи SMAPE (по ТЗ + коду)

| Факт `y` | Прогноз `ŷ` | Ошибка |
|---|---|---|
| 0 | 0 | день **исключён** из среднего (не помогает, не мешает) |
| 0 | >0 | **200%** (максимум) |
| >0 | 0 | **200%** (максимум) |
| 2 | 2.1 | ~5% |
| серия целиком 0/0 | — | 0 (идеал) |

### 2.3 Стратегические выводы (то, на чём строится всё решение)

**Вывод 1. Ноль vs маленький плюс — это бинарное решение, а не регрессия.**
На непродажном день ошибка равна 200% **независимо от величины** (можно предсказать 0.01 или 1000 — всё равно 200%). Значит, на таких днях важен **только знак**: «предсказал 0 → провал, предсказал хоть что-то → провал». Отсюда напрашивается **двухступенчатая (hurdle) модель**: сначала «будет ли продажа», потом «сколько».

**Вывод 2. «Не промахнуться по дню продаж» дороже, чем «быть точным в величине».**
Пропуск продажи = 200%. Ошибка 30% в величине = 30%. Приоритет качества: **попадание в продажные дни > точность величины**.

**Вывод 3. Метрика любит консерватизм на редких сериях.**
Серия из 8789 имеет **равный вес** в SMAPE, независимо от объёма. Малопродающая серия, по которой модель «размазала» положительные значения по всем дням, даст SMAPE ≈ 180–200 и утащит всю метрику. **Обнуление «спящих» серий — почти бесплатный приз.**

**Вывод 4. Но нулевой «предсказатель всех подряд» тоже проигрывает.**
Если модель везде ставит 0, SMAPE = 200 по всем сериям, где были продажи. Победа приходит от сочетания: **агрессивные нули в неясных днях + точные значения в продажных днях.**

**Вывод 5. Нужен отдельный сигнал «доля нулей / давность последней продажи» по серии.**
Это главный предиктор того, где ставить 0.

### 2.4 Как метрики конфликтуют (чтобы не сломать одно, чиня другое)

| Приём | SMAPE | WAPE | RMSE | Bias | RMSLE |
|---|---|---|---|---|---|
| Обнулить «спящие» дни/серии | ✅ сильно + | ➖ 0 (нули не входят в числитель) | ➖ 0 | ⚠️ может ухудшиться (mean(ŷ) падает) | ➖ почти 0 |
| Не промахиваться по продажам | ✅ + | ✅ + | ✅ + | ➖ | ✅ + |
| Поднять средний уровень прогноза (компенсировать Bias) | ⚠️ может − | ⚠️ − | ⚠️ − | ✅ + | ➖ |
| Точность на топ-сериях по объёму | ➖ | ✅ + | ✅ сильно + | ➖ | ➖ |
| Точность на мелких сериях | ✅ сильно + | ⚠️ почти 0 | ⚠️ почти 0 | ✅ + (Bias тоже по сериям!) | ➖ |

Практическое следствие: **Bias калибруется умножением положительных прогнозов внутри серии, а НЕ поднятием нулей вверх** (поднятие нулей = 200% в SMAPE).

### 2.5 Ранговая нормализация

`Score = Σ_k w_k × (rank_k − 1)/(N − 1)`, 0 — лучший. Следствия:
- Абсолютный размер улучшения не важен — важен **порядок среди участников**.
- SMAPE даёт половину скоринга: быть 1-м по SMAPE и последним по RMSLE (5%) почти всегда лучше, чем наоборот.
- Локально мы не можем знать ранги → минимизируем **сырые метрики** (в миноритарных метриках — относительно бейзлайна).

## 3. Архитектура решения (схема)

```
[CSV] → Агрегация в панель (date × warehouse × article, с усреднением по департаментам)
      → EDA + конструктор признаков (as-of cutoff, без утечек)
      → Валидация: cutoff = T-64 (и T-128) → предсказание 64 дней
      → Модели:
           B0  наивные бейзлайны (last value, среднее 28д, сезонное среднее)
           M1  CatBoost/LightGBM регрессор (log1p) — «уровень»
           M2  классификатор P(продажа > 0) — «гейт»
           M3  (опц.) регрессор только по положительным рядам — «величина»
      → Ансамбль (взвешенная сумма, вес подбираем на валидации)
      → Пост-обработка: гейт по порогу → обнуление спящих серий →
                        калибровка Bias → клиппинг
      → Сборка CSV (562 496 строк) → QA-чеклист → score.py
      → [Опц.] Docker + FastAPI с той же (или ≤180-дневной) моделью
```

Принцип: **метрика диктует архитектуру**. Мы не гонимся за «красивой моделью», мы гонимся за SMAPE-совместимым поведением предсказаний.

### 4.2 Сборка панели (каркас, доработать под фактические колонки)

```python
import pandas as pd

KEY = ["warehouse_name", "article"]

sales = pd.read_csv("sales_dataset_hakaton.csv", parse_dates=["date"])
stock = pd.read_csv("stock_dataset_hakaton.csv", parse_dates=["date"])

# 1. Агрегация по департаментам/городам — ТЗ: департаменты суммируются в паре
panel = (sales.groupby(["date", *KEY], as_index=False)
              .agg(quantity=("quantity", "sum"),
                   sales_sum=("sales_sum", "sum"),
                   n_rows=("quantity", "size")))

# 2. Остатки (char_article -> article)
stock = stock.rename(columns={"char_article": "article"})
stock_d = (stock.groupby(["date", *KEY], as_index=False)
                .agg(stock=("stock", "max")))          # проверить агрегацию на EDA

panel = panel.merge(stock_d, on=["date", *KEY], how="left")

# 3. Полная сетка дат по каждой паре + заполнение нулём (важно для корректных лагов)
combos = panel[KEY].drop_duplicates()
dates  = pd.date_range(panel["date"].min(), panel["date"].max(), freq="D")
grid   = pd.MultiIndex.from_product([dates, combos["warehouse_name"],
                                     combos["article"]],
                                    names=["date", *KEY]).to_frame(index=False)
panel = grid.merge(panel, on=["date", *KEY"], how="left")
panel["quantity"] = panel["quantity"].fillna(0.0)
panel["stock"]    = panel.groupby(KEY)["stock"].ffill()   # остаток «до следующего учёта»
panel = panel.sort_values(["warehouse_name", "article", "date"]).reset_index(drop=True)
```

## 5. Валидация

### 5.1 Схема (зеркальная к бою)
```
... [история, features as-of t0] | t0 = T-64 ....... [валидация: 64 дня] | T (последняя дата)
     всё, что ≤ t0 — только прошлое        предсказываем, сравниваем с фактом
```
В бою: cutoff = T (последняя дата), горизонт T+1…T+64. На валидации: cutoff = T-64, горизонт = последние 64 дня истории. **Полное зеркало условий.**

### 5.2 Фолды
| Фолд | cutoff | горизонт | назначение |
|---|---|---|---|
| **F1 (основной)** | T-64 | последний 64 дня | выбор модели и порогов |
| F2 (доп., если история ≥ 1 года) | T-128 | 64 дня перед F1 | устойчивость, борьба с переобучением на один отрезок |
| **F3 (API-фолд)** | cutoff, но фичи считаются **только из последних 180 дней** | 64 дня | проверка модели для Docker-задания |

Правило: **F2/F3 не трогаем при итерациях**, используем для финальной проверки гипотез — иначе «переобучимся на валидацию».

### 5.3 Анти-утечки (строго)
- Все лаги/скользящие — только **по прошлым** данным: `shift(1)` и раньше; никаких `rolling` с окном «включая текущий день».
- `cost_price`, `discount_sum`, `sales_sum` — только лагами, не текущим днём.
- Target-encoding категорий — по **обучающей части фолда** (OOF), не по всему датасету.
- Признаки для дня-горизонта `h` считаются **на cutoff**, а не на `cutoff+h`.
- Никаких признаков от «длины ряда до конца данных» и прочего, что знает будущее.

### 5.4 Локальный скоринг
Берём `score.py` из ТЗ **буквально** в репозиторий (`src/score.py`) — чтобы считать так же, как организаторы:

```bash
# сравнение кандидатов min-max против своего наивного бейзлайна
python src/score.py --truth val_truth.csv \
  --submissions candidates/naive.csv candidates/lgbm.csv candidates/ens.csv \
  --baseline val_naive_baseline.csv --method minmax --output leaderboard_local.csv
```
- `val_truth.csv` — фактические последние 64 дня в формате submission.
- `val_naive_baseline.csv` — наш наивный прогноз на тот же период (точка «=1» в min-max).
- Официально организаторы используют `rank`, но локально min-max даёт **монотонную** оценку: улучшил метрику — улучшил свой потенциальный ранг.

## 6. Признаки

### 6.1 Полный список (считаются строго на cutoff)

**А. Календарь целевого дня** (для горизонта `h`):
`day_of_week`, `is_weekend`, `day_of_month`, `week_of_year`, `month`, `is_holiday` (календарь РФ), `days_to_holiday`, `horizon h ∈ [1,64]`, `is_month_start/end`.

**Б. «Свежие» уровни спроса (as-of cutoff, по каждой серии):**
`mean/std/max/sum` за 7/14/28/56/90/180 дней; `mean_для_каждого_дня_недели` (сезонный профиль: `mean_qty[dow]/mean_qty`);
`last_value` (последнее ненулевое), `days_since_last_sale`, `n_sales_days_28`, `zero_share_28/90`,
`trend = mean(28)/mean(56)` (запасная альтернатива slope), `ema_7/28`.

**В. Мульти-горизонтные лаги** (на дату `cutoff+h`, берутся из прошлого):
`lag_7`, `lag_14`, `lag_28`, `lag_35`, `lag_64` — т.е. «значение в тот же день недели N недель назад» **от целевого дня**, но не позже cutoff. Для `h > 7` недельные лаги ещё лежат в истории — это сильнейший признак («год/месяц назад в этот же день недели»).

**Г. Остатки:**
`stock_last` (последний известный), `stock_mean_28`, `stock_zero_share_90`,
`days_of_cover = stock / max(mean_daily_sales_28, 0.1)` — «на сколько дней хватит товара»,
`stock_trend`. **Для будущего `stock` неизвестен** → `days_of_cover` даёт эвристику «кончится на день N» (настраивается на валидации, риск: пополнение).

**Д. Статики серии (target-encoding, OOF):**
`mean_qty_series`, `mean_qty_article`, `mean_qty_warehouse`, `mean_qty_category_1..3`, `mean_qty_city`,
`zero_share_series`, `n_days_series`. Плюс сырые категориалы: `warehouse`, `article`, `category_lvl_1..3`, `cities_name`, `characteristic`.

**Е. Кросс-признаки:**
`article × warehouse` (пара — ключевая единица), `category × dow`, `warehouse × dow`.

### 6.2 Каркас генерации (as-of cutoff, без утечек)

```python
import pandas as pd, numpy as np

def features_as_of(panel, cutoff, lookback=180):
    """Признаки всех серий по данным строго ДО cutoff (включительно)."""
    hist = panel[(panel["date"] <= cutoff) &
                 (panel["date"] >  cutoff - pd.Timedelta(days=lookback))]
    g = hist.groupby(KEY)["quantity"]

    f = g.agg(n_days="size", total="sum", mean="mean", std="std",
              max="max", n_sale_days=lambda s: int((s > 0).sum()))
    f["zero_share"] = 1 - f["n_sale_days"] / f["n_days"]
    f["last_value"] = g.apply(lambda s: s.iloc[-1])

    for w in (7, 14, 28, 56, 90):
        t = hist[hist["date"] > cutoff - pd.Timedelta(days=w)]
        gw = t.groupby(KEY)["quantity"]
        f[f"mean_{w}"]  = gw.mean()
        f[f"zeros_{w}"] = (gw.apply(lambda s: (s == 0).mean()))

    # сезонный профиль по дням недели (as-of)
    dow = hist.groupby(KEY + [hist["date"].dt.dayofweek])["quantity"].mean()
    f["dow_profile"] = dow.groupby(level=0).transform("mean") / f["mean_28"]

    # остатки
    st = hist.groupby(KEY)["stock"]
    f["stock_last"] = st.apply(lambda s: s.dropna().iloc[-1] if s.notna().any() else np.nan)
    f["stock_mean_28"] = st.apply(lambda s: s.tail(28).mean())
    f["days_of_cover"] = f["stock_last"] / np.maximum(f.get("mean_28", 1), 0.1)
    return f.reset_index()
```

**Важно про `lookback`:** если идём в Docker-задание одной моделью — фиксируем `lookback=180` сразу на основном пайплайне (см. §11.2).

## 7. Модели

### 7.1 Уровни решения (по нарастанию силы)

| Уровень | Что | Ожидаемый эффект | Время |
|---|---|---|---|
| L0 | наивные бейзлайны | точка отсчёта | 1 час |
| L1 | глобальный бустинг на всех сериях (уровень) | основной прирост | 2–4 часа |
| L2 | + hurdle: классификатор нулей + гейт | **главный прирост под SMAPE** | 2–3 часа |
| L3 | пост-обработка: пороги, обнуление спящих, калибровка Bias | заметный дешёвый прирост | 1–2 часа |
| L4 | ансамбль 2–3 моделей + наивных, веса на валидации | +2–5% к метрике | 1–2 часа |
| L5 | (если время) пер-серийные модели (Prophet/ETS) на топ-100 сериях | обычно мало, опционально | 3+ часа |

### 7.2 Hurdle-модель (ключевая идея)

```
Шаг 1. Классификатор P(продажа>0 | серия, день)  — LightGBM/CatBoost binary, те же фичи
Шаг 2. Регрессор ŷ_pos = E[quantity | quantity>0] — обучается ТОЛЬКО на строках с quantity>0,
        таргет log1p(quantity)
Шаг 3. Гейт:  quantity_hat = ŷ_pos, если P > τ, иначе 0
        (τ подбирается на валидации, глобально и/или по корзинам «zero_share»)
```
Почему именно так (см. §2.3): SMAPE вознаграждает точный ноль в непродажный день и точную величину в продажный. Разделяем задачи — и каждая решается проще и точнее.

Альтернатива без отдельного классификатора: один регрессор + порог по значению (`pred < τ → 0`). Работает, но слабее — модель обучалась оптимизировать величину, а не вероятность. **Берём оба варианта в бенчмарк, оставляем лучший.**

### 7.3 Обучение: сборка обучающей выборки

Строка обучающей выборки = `(cutoff t, серия s, горизонт h)`, где признаки — «на момент t», таргет — `quantity(s, t+h)`, `h ∈ [1..64]`.

```python
def build_train(panel, cutoffs, horizon=64):
    frames = []
    for c in cutoffs:
        feats = features_as_of(panel, c)                       # (n_series, k)
        fut = (panel[panel["date"] > c]
                 .assign(h=lambda d: (d["date"] - c).dt.days)
                 .query("h >= 1 and h <= @horizon"))
        tgt = fut.pivot_table(index=KEY, columns="h",
                              values="quantity", aggfunc="sum")
        tgt = tgt.reindex(feats[KEY].itertuples(index=False, name=None))
        tgt = tgt.fillna(0.0)
        tgt.columns = [f"target_h{h}" for h in tgt.columns]
        frames.append(pd.concat([feats.reset_index(drop=True),
                                 tgt.reset_index(drop=True)], axis=1))
    return pd.concat(frames, ignore_index=True)   # потом melt в long-формат

# cutoffs: каждые 7 дней (недельная сетка), начиная после burn-in на lookback
```

**Оценка объёма:** 60 cutoffs × 64 горизонта × 8 789 серий ≈ **34 млн строк**. При ~70 фичах в float32 ≈ 9–10 GB — помещается в 64 GB. Если не влезет: урезаем cutoffs до 30–40, фичи до 50, держим float32.

### 7.4 Стартовые гиперпараметры

**LightGBM (регрессор, таргет `log1p`):**
```python
params = dict(
    objective="regression", metric="mae",
    learning_rate=0.05, num_leaves=63, max_depth=-1,
    min_data_in_leaf=200, feature_fraction=0.8,
    bagging_fraction=0.8, bagging_freq=1,
    lambda_l1=1.0, lambda_l2=5.0,
    num_threads=8, seed=42,
    deterministic=True, force_row_wise=True,      # ← детерминизм (требование ТЗ)
)
# ранняя остановка по локальному SMAPE на F1 (feval), 500–1500 итераций
```
**CatBoost (конкурент, нативные категориалы — хороший выбор, если не хочется с target-encoding'ом):**
```python
cb.CatBoostParams(dict(
    loss_function="MAE", learning_rate=0.05, depth=8,
    l2_leaf_reg=8, iterations=3000, early_stopping_rounds=100,
    random_seed=42, verbose=0, thread_count=8,
    cat_features=["warehouse_name","article","category_lvl_1",
                  "category_lvl_2","category_lvl_3","cities_name"],
))
# таргет тоже log1p; expm1 при инференсе
```

**Классификатор:** те же фичи, таргет `quantity > 0`, `objective="binary"`, метрика — `average_precision` / `binary_logloss`, порог подбирается отдельно.

**Детерминизм:** `seed`/`random_seed` фиксированы, `num_threads` фиксирован, GPU-режим LightGBM может давать расхождения между машинами — **финальный прогон гоняем на CPU**. Прогноз усредняем по 3 фиксированным сидам (среднее детерминировано и стабильнее).

**Чего НЕ стоит делать на этом хакатоне:** глубокие нейросети (N-BEATS/NHITS/TFT) — 8 789 серий × короткая история × 2 дня времени = невыгодный риск/награда. Профит даёт табличный бустинг + метрика-постобработка.

### 7.5 Ансамбль
```
final = w1·(hurdle_lgbm) + w2·(catboost) + w3·(naive_сезонное_среднее)
```
`w` грузим сеткой на F1 (шаг 0.1, сумма 1), фиксируем то, что улучшило локальный `score.py`. Наивный компонент стабилизирует «спящие» серии.

## 8. Пост-обработка и тюнинг под метрики

Порядок применения (каждый шаг — только если улучшает локальный score):

1. **Клиппинг:** `clip(lower=0)`. Отрицательных быть не должно.
2. **Гейтинг по нулям:** `pred[p_sale < τ] = 0`; grid `τ ∈ {0.15, 0.25, 0.35, 0.45, 0.55, 0.65}` × корзины по `zero_share` серии (спящие / редкие / частые). Для регрессорного варианта: grid `pred < τ_val → 0`, `τ_val ∈ {0.05, 0.1, 0.2, 0.3, 0.5}`.
3. **Правило «спящих серий»:** если за последние `N` дней (grid: 10/14/21/28) не было **ни одной** продажи → весь прогноз = 0. Обычно это самый дешёвый прирост SMAPE.
4. **Калибровка Bias:** внутри серии `pred *= k`, где `k = clip(целевое_среднее / mean(pred), k_min, k_max)`, `целевое_среднее` — устойчивая оценка (например `mean(last 28 дней)` с учётом тренда `mean28/mean56`). `k_min/k_max ∈ {0.9/1.1, 0.85/1.18, 0.8/1.25}`. **Умножение не создаёт плюсы на нулевых днях** (0 × k = 0) — поэтому не портит SMAPE.
5. **Глобальный множитель** `c ∈ {0.97, 1.0, 1.03}` — тонкая настройка баланса Bias ↔ WAPE/RMSE.
6. **(Опц.) Кап по `days_of_cover`** — если прогноз на день `d` превышает остаток, накручиваем вниз (работает только при подтверждённой на EDA связи «остаток 0 ⇒ продаж 0»).

Всё тюнится **координатным перебором на F1**, финально проверяется на F2/F3.

## 10. Бейзлайны и ориентиры

| Модель | Описание | Зачем |
|---|---|---|
| `zero` | везде 0 | нижняя граница (SMAPE ≈ 200 на активных сериях) |
| `last` | последнее известное значение (наивный бейзлайн организаторов) | точка «=1» в min-max |
| `mean28` | среднее за последние 28 дней | крепкий простой старт |

### 11.2 Ключевой дизайн-инсайт: признаки должны быть глубиной ≤ 180 дней
Контейнер **не имеет доступа к обучающей выборке** — на вход приходят только последние ~180 дней. Если наша основная модель использует `lookback=365`, в API-режиме фичи посчитать не из чего, и веса не встанут.

- **(А, рекомендую)** Делаем весь пайплайн с `lookback=180` — тогда **одна и та же модель** работает и в основном сабмите, и в контейнере. Проверяем на EDA, что истории хватает (F3-фолд: валидация при `lookback=180` не должна проседать).

Прочие правила инференса: никакой загрузки из интернета, `random_seed` зафиксирован, фиксированное число потоков, никаких `time.now`-признаков.

## 14. Финальный чек-лист сдачи

## Приложение A. Мини-глоссарий

- **Ряд/серия (time series)** — продажи одной пары «склад × товар» по дням. У нас до 8 789 рядов.
- **Признак (feature)** — входная переменная модели (день недели, среднее за 28 дней и т.д.).
- **Таргет** — то, что предсказываем: `quantity`.
- **Утечка (leakage)** — когда признак случайно «знает» будущее. Главный источник красивых, но ложных результатов.
- **Переобучение** — модель запомнила шум истории и плохо работает на будущем.
- **Бустинг (LightGBM/CatBoost/XGBoost)** — семейство моделей, «умные деревья», стандарт табличных хакатонов.
- **Hurdle-модель** — «двухступенчатая»: сначала «случится ли событие», потом «какой размер».
- **Гейт / порог** — правило «если вероятность продажи < τ → ставим 0».
- **Калибровка** — подгонка среднего уровня прогноза (для метрики Bias).
- **Фолд / кросс-валидация** — отрезки истории для честной проверки модели.
- **Инференс** — получение предсказаний обученной моделью.
- **Детерминированность** — одинаковый вход → одинаковый выход, запуск в запуск.

## Приложение B. Локальная реализация метрик (зеркало `score.py`)

```python
import numpy as np, pandas as pd

W = dict(smape=0.50, wape=0.20, rmse=0.15, bias=0.10, rmsle=0.05)

def _smape_series(y, p):
    den = (np.abs(y) + np.abs(p)) / 2.0
    m = den > 0
    if not m.any():
        return 0.0
    return float(np.mean(np.abs(y[m] - p[m]) / den[m]) * 100.0)

def evaluate(df_true, df_pred):
    """df_*: колонки date, warehouse_name, article, quantity."""
    assert not df_pred.duplicated(["date", "warehouse_name", "article"]).any()
    df = df_true.merge(df_pred, on=["date", "warehouse_name", "article"],
                       how="left", suffixes=("_t", "_p"))
    df["quantity_p"] = df["quantity_p"].fillna(0).clip(lower=0)
    y, p = df["quantity_t"].values.astype(float), df["quantity_p"].values.astype(float)
    sid = (df["warehouse_name"].astype(str) + "|" + df["article"].astype(str)).values
    g = pd.DataFrame({"sid": sid, "y": y, "p": p}).groupby("sid")

    smape = g.apply(lambda d: _smape_series(d["y"].values, d["p"].values)).mean()
    wape  = np.abs(y - p).sum() / np.abs(y).sum() * 100
    rmse  = np.sqrt(np.mean((y - p) ** 2))
    bias  = g.apply(lambda d: (np.nan if d["y"].mean() == 0 else
                    abs(d["p"].mean() - d["y"].mean()) / d["y"].mean() * 100)
                   ).dropna().mean()
    rmsle = np.sqrt(np.mean((np.log1p(p) - np.log1p(y)) ** 2))
    return dict(smape=smape, wape=wape, rmse=rmse, bias=bias, rmsle=rmsle)

def composite(m, base):
    """Min-max против бейзлайна: 0 = идеал, 1 = бейзлайн (как в score.py)."""
    return sum(W[k] * (min(m[k] / base[k], 1.0) if base[k] else 0.0) for k in W)
```
